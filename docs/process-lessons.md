# Process lessons

Lessons about this repo's development process, drawn from building its skills, for the process components the HLD plans (review-wave orchestration, the spec-review loop). The numbers behind them are in [the review log](review-log/README.md).

## Slices and specs

- **Specs grow in review.** A slice estimated before the EARS coverage review can double or more (session-wrap-up's second slice went from 8 specs to 38): coverage gaps and edge-audit forks add specs. Count a slice's specs after that review, and re-cut it if it passes about 40.
- **Cut slices from the work that waits on them.** Before proposing a slice plan, list the tasks that depend on the work (`tasks why <ID>`) and what each one actually needs. Order the slices so the earliest one unblocks the most valuable of them, and make each slice a subtask so its dependents can point at that slice, not the whole task. Put each data fix in the slice that adds the rule requiring it, so every slice ends with checks passing. The task tracker's first plan, layered by component (data, then ranking, then the skill), would have left everything waiting until the last slice. Its lint would also have failed checks for two slices while the data fixes waited.
- **Spikes before EARS pay off.** Running the platform behaviors a design depends on (memory paths, session listing, the eval runner) removes wrong assumptions before any spec is written. Record the results as facts in the LLD.
- **Check the HLD's own summary of the component.** When a change alters what a component does, grep the HLD for its summary at the HLD check. AD-6's check missed a line that still described the session wrap-up's old cross-repo routing, until the code review found it.

## Review and evals

- **Evals find what review waves don't.** After six review waves on session-wrap-up's first slice, eval runs still found 8 skill-text misses and 9 grader or prompt faults. Run a skill's evals before its slice is committed.
- **Trial the riskiest cases first.** Run a new suite's riskiest cases on the real model before the full set. For session-wrap-up's second slice, two cases cost $0.37 and found four faults.
- **Run the whole suite when a report gains a section.** Session-wrap-up's slice 3a passed its new cases, then the full suite failed seven more: the new state check exposed scaffolds that didn't match their records, and the new section gave the agent room to invent follow-ups.
- **Put an output rule in the output's template.** In session-wrap-up's slice 3b, rules stated in a step's text kept slipping, even after rewording. Moved into the report template's placeholder lines, which the agent copies as it writes, they mostly held.
- **Set a last round before starting it.** Once each remaining miss was down to one run in three, a final round was named in advance, and what still slipped was logged with its rate instead of starting another round.
- **Re-run a surprise before diagnosing it.** Two of three single failures passed twice on re-run. The third failed again, and was a real trigger gap.
- **Size an eval's scaffold like real data.** With four tasks in its backlog, an agent in the search-before-create case found the match by listing the task files, the shortcut the case was meant to rule out; with forty, it searched.
- **Know when to stop reviewing.** Yield fell from 40 to 12 to 5 to 5 findings across one slice's code-review waves. Two narrow re-checks after the main wave were the useful stopping point. Review waves now follow the [review-stopping decision](decisions/review-wave-stopping.md): fresh full-scope waves until triage accepts nothing to fix.
- **Review a prototype before it joins `check`.** The task-tracking pilot was built outside LID with its tests passing. Its first review wave found 12 defects in about 600 lines, among them a lint rule that would have failed CI on the first GitHub blocker and two paths that failed open. A mutation sweep by the test reviewer found about twenty behaviours no test would catch; run the sweep without `-x`, or the first test to fail hides which test really covers a behaviour.
- **State each value once.** A value written in two places drifts: a re-check found OpenAIRE's rate limit given as 7,000 in a route table and 7,200 in the same file's rate-limit section, a day after both were written. Keep it in one place and point to it.
- **Replay the event orders a probe recorded.** Hook tests built from the order the design assumed passed (124 of 124) while a foreground subagent was never asked and no notes were captured: Claude Code fires those hooks in another order, which the probe's logs already showed. When code reacts to platform events, record the observed order as a fact in the LLD, and test whole flows in that order.
- **Check a hook fix live.** Claude Code re-reads a hook script registered from the repo on every event, so the next launch in the session that found the bug exercises the fix. On 2.1.323, a background launch made right after the agent-type fallback landed got its counting line and its notes, which the pytest replays couldn't show.
- **Brief reviewers with what they can't see.** Blind divergence readers flagged gaps the design's Terms section already closed, because their brief held only the specs file's header: give them a glossary of the terms the specs use, and say whether ambiguity older than the change is in scope. Tell a code or doc reviewer which state it reviews (HEAD, the index or the worktree), to leave lock files out of diffs, and where a dependency's installed source is. For a large change, tell it to list hunks with `git diff HEAD -U0 | grep '^@@'` and read the changed ranges in the files, since a whole diff of long-line docs gets saved to a file instead of shown. Give a reviewer of a note or design the config files and sibling repos it cites as sources, and tell it to open them: in one note review the worst error (an auto-merge setting) showed only in a Renovate preset, and two more needed the template repo's own files.
- **Give a script's exit status 1 one meaning.** An uncaught Python exception exits 1, so a script whose status 1 means "differs" or "a check failed" reports a crash as an ordinary result. The parallel-sessions code review found this in all three of its scripts; each `main` now catches anything unexpected and exits 2.
- **Have the tests' inspector run mutants.** Ask the reviewer of a slice's tests to run them against mutated copies of the code, one wrong behaviour per copy. On the harvester's lookups by ID, 15 of 21 mutants survived tests that had passed a plain reading, and closing them took 21 more cases.
- **Mark only what a run reached.** Mark a spec `[x]` from an eval run only when the run reached the spec's own condition. One that held because its trigger never arose (no fallback, no later failure) stays open, and the review-log row lists it under what never arose. Two harvester specs were first marked on a run that never reached them.

## Approval steps

- **Put the text inside the question.** A question dialog can hide the conversation above it, so an approval step that asks through a question tool puts the exact text in the question itself (for example, in each option's preview).
- **Keep each preview short enough to show whole.** A long preview is cropped ("8 lines hidden"), hiding exactly the text being approved. Give each item its own question (a question tool can ask several at once), so each preview holds one item's text.
- **Every option shows the text it would apply.** An option that applies only part of a change ("only item 4") previews that part. One with no preview leaves the developer approving text they can't see.

These apply to session-wrap-up's approval gate in slice 3b.

## Research and sources

- **Check a source's terms and live behavior before recommending it.** Read the service's terms and robots.txt, and probe it, before a route goes into a skill. A first probe recommended Arch's package search, which its robots.txt disallows, and rated OpenAlex the primary paper route a day before its anonymous search was paused under load.
- **Measure a script against a capable baseline.** In the harvester's paired run, the by-hand arm wrote its own paced `curl` script, so the harvester saved 29% of subagent tokens, not the 50–65% estimated against one call per query. Brief the baseline arm to work as agents actually do, and say which baseline a saving is against.
