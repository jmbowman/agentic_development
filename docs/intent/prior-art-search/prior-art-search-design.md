# Prior-art search skill

## Context and Design Philosophy

Agents recommend building tools from scratch when an existing tool already does most of the job, or a library would halve the work, and they turn the alternative up only when pressed. Searching once, in one place, with one phrasing doesn't fix that. A search that misses the best candidate looks the same as one that proves nothing fits.

This skill makes the search a fixed procedure with an auditable result. An agent runs it before recommending that a tool, library, script, subsystem or agent skill be built or substantially extended, after the goal and requirements are clear and before detailed design. The skill:
- searches against the underlying need, not the solution shape someone proposed;
- covers a set of sources chosen by the need, and logs each as searched, excluded with a reason, or unavailable;
- follows each good candidate to the next round, and stops when a round adds nothing;
- classifies candidates as adopt, build on, borrow ideas or reject, citing each license from its license file;
- verifies the top candidates' claimed limitations in their source, not their docs;
- reports a verdict whose "nothing fits" can be checked, and saves it as a dated note in the host repo.

Scope is software: tools, libraries, components, services with an API, scripts, and agent skills, plugins and MCP servers. Where a need is about an approach or technique more than a tool, published research on it (papers, surveys, theses, technical reports) is searched too, and what it yields is borrowed ideas, not software to adopt. Choices that aren't software (purchases, providers) use different sources and criteria, and are out of scope.

The skill is self-contained (HLD tenet 7). Its read-only clone procedure is part of the skill, and it uses a host repo's own reference-clone convention when the host's instructions name one. It is portable (tenet 8). The frontmatter uses only Agent Skills fields, and the instructions work in any agent that can search the web and run `git`; reading the optional access settings also needs Python 3.11 or later. The optional harvester needs `uv` and a POSIX system (it locks files with `flock`), and without them the agent sends those requests itself. Under Claude Code, parallel subagents are an optional speed-up for searching and reading.

Several parts of the method come from existing skills, recorded in [the prior-art note](../../prior-art/2026-10-17-prior-art-search-skill.md): the coverage ledger with route triggers, support values that keep "unverified" separate from "unsupported", one-way vs. two-way doors to set effort, a native-feature audit first, and reference-only handling for unlicensed code.

## When it runs, and how hard

The skill's description triggers it when an agent is about to recommend or start building a new tool, library, script, subsystem or skill, or to substantially extend one. *Substantially extend* means adding a new capability or a new external dependency, as opposed to changing behavior that already exists. It also triggers when someone asks whether something already exists. When someone asks which approaches or techniques help reach an objective and nothing is being built or extended, the agent asks whether they want to use the skill, and doesn't start the search until they say yes; in a non-interactive run it doesn't start, and records the question as unanswered. It doesn't trigger for:
- bug fixes;
- refactors inside existing code;
- a dependency the project already uses;
- a tool someone has already chosen and wants help using;
- a custom piece named in the skill's own report, such as the custom part of a blend.

Before searching, the agent picks an effort level and states it with a one-line reason:
- **Quick pass,** for a two-way door: a choice that is cheap to reverse, such as a small utility, or a dependency with several substitutes. It runs steps 0-6 with at least two searched routes and one snowball round. It reads the primary page and license of each candidate it will present, classifies those, and reports in the conversation, listing any other candidates it found as seen but not classified: the verdict, the candidates it classified with their licenses, and the coverage ledger with its queries. Unless the developer chose it, a quick pass concludes only **adopt** or **build on**, or **findings** for an approach-only need; anything else escalates (below). Saving a note is optional.
- **Full method,** for a one-way door: a choice that is expensive to reverse, such as a new subsystem, a long-lived dependency, a tool every repo will adopt, or anything the developer flags as long-lived. It runs every step and saves a note.

A quick pass escalates to the full method when it would conclude anything other than **adopt**, **build on** or (for an approach-only need) **findings**, when two candidates are close (both meet every hard criterion on the evidence read so far), or when its best candidate leaves part of the core need unmet and no other candidate covers that part. Building a small extension on a base the candidate is designed to be extended with isn't a gap. A core requirement that nothing found supports is. The agent switches as soon as the condition is evident, and in any case when it classifies the candidates it will present (step 7), before it reports. The ledger and candidates found so far carry over, routes excluded only because of the quick pass are searched or given a reason tied to the need, and the agent restates the level with its reason. The developer can choose the level. When the developer forces a quick pass that would otherwise escalate, the report gives its verdict as **unaudited (quick pass by developer choice)**. In a non-interactive run, the agent picks the level by these rules alone.

## Terms

- **Serious candidate:** a candidate that addresses at least part of the core need and isn't yet excluded by a hard criterion, on the evidence read so far.
- **Round:** round 1 is the queries of step 5. Round *N*+1 is the queries seeded by round *N*'s new serious candidates.
- **Route:** one place to search, such as a package registry, a forge's search, a catalog, an awesome list or general web search. A route is *triggered* when the need has a signal its trigger names (a language, "agent skill", "MCP", "hosted service", or a question about an approach or technique).

## Steps

0. **Check what's already known.** Read the host repo's recorded decisions and earlier prior-art notes on the topic, and ask the developer what they already know about or have dismissed. In a non-interactive run, record the question as unanswered and go on.
1. **State the need.** For each requirement, ask "goal or means?" and record the underlying need beside it. The search runs against the needs, and a proposed shape is one candidate design among others. Ask the developer for the two or three most common ways the result will be used, and record them with the need: step 11 walks them first, and a quick pass checks each candidate it presents against them before classifying it. Uses the request already names are recorded without asking. In a non-interactive run, record the question as unanswered, and infer the two or three most likely uses from the need, labeled as inferred, for those checks: most unattended runs would otherwise skip them.
2. **Set the criteria.** Hard pass/fail constraints come first, then lightly weighted preferences. The default criteria for software:
   - license, including compatibility with the host repo's license and how it's distributed (a hard criterion by default);
   - maintenance and ownership;
   - an acceptable runtime and language;
   - support from the stack's own automation (for example, whether Renovate can update it);
   - maturity: age, maintainers, release cadence.
3. **Re-validate what's inherited.** Recommendations from earlier notes or sessions found in step 0 are checked against the current needs and criteria. Each one that survives joins the search as a candidate, not as a conclusion.
4. **Audit what's native.** Check whether the host stack's existing tools, platform features or installed dependencies already cover the need, fully or partly. A native feature is a candidate like any other.
5. **Search,** using the coverage ledger. Each route in `references/sources.md` whose trigger matches the need's signals is selected. A selected route ends in one of three states:
   - **searched,** with at least 2 differently worded queries (the two sorted runs of one GitHub search counting as one wording), or, for a route used only to look papers up (Semantic Scholar's recommendations and exact-title lookups), with at least one seed or title whose recommendation or lookup ran, each recorded in place of a query;
   - **excluded,** with a concrete reason tied to the need ("not relevant" alone isn't a reason). In a quick pass, "quick pass" is also a valid reason, which keeps the pass quick and leaves the gap visible;
   - **excluded** without a request, with the reason "blocks scripted clients", for a route `references/sources.md` marks so: one that answers automated clients with a challenge, or whose `robots.txt` disallows the paths the route needs. Its row names an alternative way to reach the same projects, which the agent searches instead (and records in the ledger as that alternative's own route). Since the route can't be searched by any agent, its exclusion doesn't block **build**;
   - **unavailable,** with a diagnosis (authentication, rate limit, network, no such tool, or setting not set), made after one retry of a request the agent sent itself, or after the retries the harvester gives its own requests (see Harvester); a route whose required setting isn't set needs no request, so it gets no retry.

   Every service stays within its stated rate limit, which `references/sources.md` lists with where it is stated. A service that states a different limit for requests that carry its setting's value (a key, or Crossref's contact address) is held to that limit when the setting has a value (every request to it then carries the value; see Access configuration), and to its other limit otherwise; that limit takes precedence over any pace `references/sources.md` gives in place of a stated figure. Because a value travels only through a shell variable or the harvester (see Access configuration), every request to a service whose setting has a value is a shell command, never the agent's own fetch tool. Where `references/sources.md` gives a pace for a service in place of its stated figure (because that figure is a pool shared by every anonymous client, say), the run keeps to that pace. The limit belongs to the service, not the route (the GitHub search routes share one budget, and arXiv's API and listing pages share one limit), and covers all of the run's requests to it, the agent's and its subagents' together, since some services (arXiv among them) count every machine under one person's control as one client. Where no limit is stated, the default is one request every 3 seconds. A service gets one request at a time unless it states a concurrency allowance for the access the run uses; no two subagents get the same service at once, and other requests to a service go through the agent that holds it; after a rate-limit response to a request the agent sent itself, it waits as long as the service says (15 seconds if it says nothing) before its one retry; the harvester applies its own retry rules to its requests (see Harvester). Requests the agent sends with a tool that can set headers carry a user agent naming the skill and its repository, as crates.io requires and Crossref and Wikimedia ask, never the developer's address, and the agent uses the lighter access a service prefers (crates.io's sparse index for a known name) where `sources.md` names it.

   Queries are built only from the stated need: never from private identifiers, internal names or the host repo's code. Each route starts with short, broad queries and narrows with the vocabulary its first results use, since long, specific queries return little. The keyword-collision rule (Searching the literature) and each route's own tactics in `references/sources.md` still apply. A query doesn't OR several products or vendors together, since an OR across several returned hits for the first alone; each gets its own query.

   **GitHub.** Topics are discovered, not guessed. GitHub's topic search (`search/topics`) lists the topic names that exist for a term, and a field's projects spread across variants (`mdbook-plugin` and `mdbook-plugins`, `mdbook-preprocessor`, `mdbook-renderer`), so the agent looks up each of the need's key terms and each serious candidate's name there. In round 1, and for a topic variant first found in a later round, each repository search, including a `topic:` search for a variant that fits the need, runs twice: sorted by stars, and restricted to repos pushed in the 12 months before the run (a `pushed:>` date), the same window as the literature's recent-preprint step, sorted by update time. Sorting by stars alone hides new and unstarred tools, and sorting by update time alone is mostly churn and spam. Other snowball searches run once, sorted by stars, which keeps rounds within GitHub's search limit; their seeds come from candidates already found, which stars rank well. A topic-name lookup returns names, not repos, so it runs once. Each topic lookup and each sorted search counts as a query in the coverage ledger.
6. **Snowball.** Each new serious candidate seeds the next round: its topics and tags, the topic variants that GitHub's topic search finds for its name and its topics, "alternatives to" pages, awesome lists that mention it, its equivalent in other languages, and its dependents. The search ends when a round adds no new serious candidate, or after round 10. In that second case, the report says the cap was reached. Before concluding that nothing fits, the agent tries the new vocabulary it has learned plus at least one route it hasn't used.
7. **Classify** each serious candidate, provisionally: **adopt**, **build on** (a library or base to extend), **borrow ideas** or **reject**. Each gets a one-line reason and its license, recorded per Verification. A paper is classified **borrow ideas** or **reject**, and records what was read of it instead of a license (see Searching the literature). Popularity and install counts show where to look, not whether a candidate works.
8. **Fill the matrix.** Every criterion for every serious candidate gets a support value: `native`, `partial`, `extensible`, `unsupported` or `unverified`. Each value cites a source, or says "not found". `unverified` never becomes `unsupported` without evidence.
9. **Verify in source.** Candidates are ranked first by how many hard criteria they support, then by preferences. The agent verifies the top two; every serious candidate if there are three or fewer; and the third when it is close to the second.

   If no verified candidate is provisionally classified **adopt**, verification continues down the ranking, one candidate at a time, re-ranking after each as source evidence changes matrix values. It stops when a verified candidate is provisionally classified **adopt**, or when every remaining serious candidate has been verified or fails a hard criterion that reading its code can't change, such as its license or its language and runtime.

   Each claimed limitation is tagged *verified in source (path:line at commit)* or *docs only*. A hosted service or closed-source candidate can rank in the top 2-3, but its limitations are always *docs only*, and the report says so. A native feature is verified against the installed code or its pinned docs. A reading counts as verification only when it is a `full` read: the files the claim concerns, read from start to end (for a long file, the complete cited function or section and its callers on the claim's path), or, for a claim that something is absent, a `listing` whose scope covers the claim. A candidate that a subagent read only in `snippet` depth stays unverified for step 9: the main agent reads the relevant files itself, or has a subagent re-read them in full, before the candidate counts as verified or a limitation is tagged *verified in source*. A quick pass has no step 9, so it tags nothing *verified in source*.
10. **Evaluate blends.** Check whether a combination of candidates, or a candidate plus a small custom piece, beats any single one. A partial match is labeled as a building block.
11. **Walk scenarios.** Walk each finalist first through each common use the developer named in step 1, then through 2-4 concrete change scenarios that fit the need, such as a new requirement, a one-off override, a fresh CI clone, an automated upgrade PR, or a reader on GitHub. The developer's own uses come first because generic scenarios can pass a design that fails the way the result is actually used. The final classifications are set after this step.
12. **Report and save** (see Report).

## Searching agent skills

When the need is an agent skill, plugin, MCP server or prompt pack, the skill-catalog routes in `references/sources.md` trigger. These include:
- skill directories and finders, such as skills.sh;
- Claude Code plugin marketplaces;
- the MCP Registry;
- Anthropic's public skills repo;
- awesome lists for agent skills;
- GitHub topics such as `agent-skills` and `claude-skills`.

Catalogs are used through their websites or APIs, never by installing a catalog's own finder skill. skills.sh and the MCP Registry have JSON search endpoints, Claude Code's official plugin marketplace is a JSON file that is searched locally, and PulseMCP's search page is read as HTML; the other catalogs are searched through web search and GitHub. Three checks apply on top of the steps:
- **Read the skill's own files:** `SKILL.md` and every file it references, including scripts and hooks. For a plugin that bundles many skills, read only the skills under evaluation and what they reference.
- **Check portability.** Does it use frontmatter fields outside the Agent Skills spec, or tools or connectors that only one agent provides? Does it need an install step, a service or credentials?
- **Treat scanner output as flags, not verdicts.** Existing scanner results are read as leads. The agent doesn't run scanners itself.

## Searching the literature

When the need asks which approach or technique helps, or the software routes find no implementation of a requirement, the literature routes in `references/sources.md` are selected in addition to the software routes, as soon as a later round shows that no implementation exists when that is the trigger. A quick pass may exclude them with a reason ("quick pass" is a valid one), or count them among its searched routes. A paper is a *serious candidate* when its abstract page shows that it addresses the approach question with some evidence. Rules on top of the steps:
- **Papers stay outside the software pipeline.** A paper gets no row in the matrix, takes no place in the ranking, and isn't verified in step 9. It goes in a papers table instead, and its license is recorded as "n/a". A paper's published artifact (its code repository, dataset or supplementary material) is a software or data candidate in its own right, with a license read as usual.
- **Classes.** A paper is classified **borrow ideas** or **reject**, never adopted. Software candidates are classified as usual, and the report links a software candidate that implements a technique a named paper describes to that paper.
- **No source to verify.** A paper's claims are tagged *paper-reported*, never *verified in source*, unless the agent checked the claim in the paper's published artifact. Each paper also records one value from each list:
  - read state: *read in full*, *read in part* (naming the sections), *abstract only* or *not retrievable*;
  - evidence strength: experiment, weak experiment, observational study, qualitative study or untested proposal;
  - review status: peer-reviewed, preprint, thesis, or unreviewed report (a vendor report is an unreviewed report).

  A claim from an abstract-only or preprint-only source is attributed to that source ("the abstract reports…"), not stated as established. A subagent reading papers returns paper records in the shape `references/verification.md` defines.
- **Legal copies only.** Full text comes from a copy that the author, the institution or the publisher hosts, that a resolver (such as an OpenAlex DOI lookup) reports as open access, or that the developer lawfully obtained and put in the project. The agent never uses shadow libraries or copies posted without the rights-holder's consent, and never works around a paywall. When no legal copy is reachable, the paper is *abstract only*.
- **Quoting.** In a public repo, the note holds paraphrase and brief cited quotations from a paper. The developer's supplying a paper's file doesn't count as approval to publish its text.
- **Worth retrieving manually.** A paper that is *abstract only* and whose abstract reports a result bearing on a hard criterion or on the verdict goes on a list in the report and the note, with its DOI (Digital Object Identifier, the permanent ID that resolves to a paper), why it matters, and the legal ways to get it (the publisher's pay-per-article page, a library or interlibrary loan, an author request, a membership the developer holds). The skill neither quotes nor looks up a price. When the developer supplies the file, the agent reads it, updates that paper's read state, claims and class, and removes its entry from the list, in the saved note in place or in the report when no note was saved. When neither is at hand, it asks for the note's path. It revisits no other paper's class, and when what it read bears on the verdict it tells the developer and doesn't change the verdict silently.
- **Snowballing** follows citations, in each round and in this order: backward (a paper's references), forward (papers citing it), related (recommendations, related works), then the vocabulary the papers use, then arXiv preprints submitted in the last 12 months.
- **Which service for what.** OpenAlex is the default for keyword search, citations and references: its data is CC0, its lookups and filters keep working when its search is paused, and it indexes recent arXiv preprints with their citing works. Semantic Scholar is used only for what OpenAlex lacks: recommendations from a seed paper, and exact-title lookups of publisher-only landmark papers. Its keyed requests are refused at busy times well below its stated limit, so its searches aren't worth their retries. OpenAlex is its substitute: related works in place of recommendations, and a title search in place of an exact-title lookup.
- **Reliability.** Several literature APIs throttle or fail for stretches while their lookup calls keep working. The retry-once rule applies to requests the agent sends itself; the harvester's Semantic Scholar requests get a longer schedule (see Harvester). Each literature route names a different literature route as its substitute. When a route is unavailable and its substitute was searched, the outage doesn't block the verdict **build**, and the report lists the route under "Could not verify".
- **Keyword collisions.** Ambiguous words ("diff", "agent", "state machine", "comprehension") return unrelated fields, so each query pairs them with a software-specific term, beside the ambiguous word, not in place of it.

## Access configuration

Some routes work better with a credential or a contact address: a literature API's free key, or the contact email that a resolver requires. The skill reads these from an optional TOML file, `.config/prior-art-sources.toml` in the host repo, with Python 3.11 or later (`tomllib`). When the system Python is older, the agent reads it with a Python that `uv` provides; with neither, the run proceeds as if there were no settings file. The agent and the harvester (which always runs on `uv`'s Python) thus read the file whenever either can, so a service never gets keyed requests from one and anonymous ones from the other. The template, `references/settings.example.toml`, ships inside the skill, so every host repo that installs the skill gets it. It lists every setting with a blank value, where to register, and a pointer to the service's terms, and a developer copies it to the host's `.config/` and fills it in. `references/sources.md` names which route uses which setting, and tells a host repo to ignore the file. This repo gitignores the real file. Each setting in the template is marked `required` (the route can't work without it, such as a registry API that rejects requests without a key) or `optional` (a key that makes a route faster or more reliable). Rules:
- With no file, or no value, a route whose setting is `optional` is searched without credentials. A route whose setting is `required` is recorded unavailable ("setting not set") and isn't searched, and like any unavailable route it blocks **build**. A route that uses a setting and is still throttled after its retries, with no value set, is recorded unavailable ("rate limit, no key set"); with a value set, or on a route that uses no setting, the diagnosis is "rate limit". OpenAlex pauses anonymous searches under load with an HTTP 503 whose message names the key; that is a rate-limit response like any other, not a rejected key, since OpenAlex's lookups keep working meanwhile. The agent doesn't invent a value or take one from any source but the settings file (the environment, global git configuration, other files).
- When a setting has a value, every request the run sends to its service carries it, from the first request on, whichever agent sends it. A service that rejects its API key (an HTTP 401 or 403 that isn't a rate-limit response, which carries a `Retry-After` or rate-limit header or says a limit was reached) makes its routes unavailable ("authentication: `<setting>` rejected"), and the run sends it no further requests, with or without the key, so there is no fallback to anonymous access; the report tells the developer which setting was rejected. A contact address, such as Crossref's, is never treated as rejected, since the service doesn't check it.
- Before reading the file, the agent checks that git ignores it. If it doesn't, the agent treats the run as having no settings file, doesn't read it, and asks the developer whether they want the agent to add the line to the host repo's `.gitignore`. It doesn't edit that file unless the developer says yes, and in a non-interactive run it doesn't edit it and records the question as unanswered.
- A value is sent only to the service it belongs to, which is a narrower rule than Verification's ban on sending credentials to candidates. In a request the agent sends itself, it travels as the parameter or header the service requires, which `references/sources.md` names for each setting, through a shell variable set from the settings file in the same command, so the command text holds the variable and not the value. The harvester reads the file and passes values to its connectors itself (see Harvester, Credentials). It never appears in a prompt, a record, a query or URL the agent writes down, a report, a note, the conversation, or the literal text of a command. The agent never opens the file with a file-read tool, which would put the values in the conversation. A subagent that needs a value reads the file itself, once the main agent has confirmed that git ignores it, and the main agent puts these rules in each subagent's prompt.
- The agent never registers for a key on the developer's behalf, even where a service offers agent-issued keys.
- The agent never stages or commits the file.

## Harvester

The harvester is a script that sends a batch of literature queries for the agent and writes what came back to disk. The agent chooses the queries, reads the results and classifies papers. The harvester only paces, sends, logs and summarizes. That mechanical work costs an agent many tokens when it sends requests itself: it keeps raw responses in its context, makes several calls per query, and formats records by hand. And a query that fails inside a shell pipeline can vanish with no error and no record. The harvester records every query it was given, with what happened to it.

**Scope.** The harvester covers three literature routes: arXiv, OpenAlex and Semantic Scholar. It runs keyword searches on arXiv and OpenAlex; for OpenAlex, the works that cite a paper and the works it references (the forward and backward steps of snowballing); and every request the skill sends to Semantic Scholar: recommendations from seed papers, and exact-title lookups. Every other route, and every other kind of request to arXiv and OpenAlex (DOI and open-access lookups, arXiv ID lookups and listing pages, reading full text), is still sent by the agent itself under the rules in Steps and Access configuration.

**Base.** The harvester uses [paper-search-mcp](https://github.com/openags/paper-search-mcp)'s connectors as a library, from a fork, [jmbowman/paper-search-mcp](https://github.com/jmbowman/paper-search-mcp). The fork's `integration` branch adds a shared HTTP layer, `paper_search_mcp.http_limits`, which is to be proposed upstream once the harvester works end to end. That layer creates every connector's session and paces each request to a limit table keyed by host. It records slots in SQLite, which processes can share through a directory named by `PAPER_SEARCH_MCP_RATE_LIMIT_DIR`, and it raises `RateLimited` instead of waiting longer than its adapter's `max_wait`. It never retries. The harvester's PEP 723 header pins a commit of the fork's `integration` branch, and its lock file pins every other dependency. When upstream releases the shared layer, the pin moves to upstream. [The harvest pipeline note](../../prior-art/2026-11-07-search-harvest-pipeline.md) records the search behind the blend, with [litsurvey](https://github.com/udaykdk/litsurvey) as the fallback base. That note planned a limiter of the skill's own on PyrateLimiter; the Harvester base row of Decisions & Alternatives explains why the limiter moved into the fork instead.

**Running it.** The agent runs `uv run --script <skill>/scripts/harvest.py`, with:
- one action, with the services it takes:
  - `search`: keyword search, on `arxiv` or `openalex`;
  - `citations` and `references`: on `openalex`, for papers given by DOI or OpenAlex work ID;
  - `recommend`: on `semanticscholar`, for seed papers given by DOI, arXiv ID or Semantic Scholar paper ID;
  - `lookup`: on `semanticscholar`, for papers given by exact title;
- one service;
- the round number;
- the run directory;
- the number of results to fetch per query: 50 by default for a search (at most 100), and 100 for citations, references or recommendations (at most 500); a lookup returns its one best match;
- the number of results per query to print in the summary (10 by default);
- the queries, paper IDs or titles.

`references/harvester.md` gives the exact command.

Fetching and printing are separate because services count requests, not results. A search page of up to 100 results is still one request on arXiv and OpenAlex, a citations or references page holds up to 100, and one recommendations request returns up to 500. So the harvester fetches deep pages into `records.jsonl`, where they cost the agent no tokens, and prints only the top results. The agent filters the records file when it wants the rest, such as every citing work whose title mentions a term. Snowballing gains most: a well-cited paper's first ten citing works are a thin forward step. Going past 100 citations or references takes more pages, within the connector's own page and request budget.

The run directory belongs to one skill run, and the main agent passes its path to each subagent. It is in the agent's scratch directory, or in a directory the host repo's git ignores, so raw payloads stay out of the host repo's history. Several invocations can use it at once:
- each invocation has its own ID, which prefixes its query IDs;
- each invocation appends to the shared files while holding an operating-system file lock (`flock`), which is released when the process ends, so a killed process never leaves a stale lock.

**In a sandboxed shell.** An agent's shell may be sandboxed so that it can write only inside the host repo, as Claude Code's sandbox does (and every `claude plugin eval` run uses it). Then neither the agent's scratch directory nor uv's cache under `~/.cache` is writable, and the harvester can't start. So:
- the run directory goes in a directory at the top of the host repo that git ignores, such as `tmp/`, as `<ignored>/prior-art-search/<run>`. When there is none, the agent asks the developer whether to ignore one, under the same rule as for the settings file's ignore line; in a non-interactive run it sends the requests itself;
- when `uv` fails because it can't write its cache, the agent runs the harvester again with `UV_CACHE_DIR` set to `<ignored>/prior-art-search/uv-cache`, and falls back to sending the requests itself only if that fails too;
- when the shared limiter directory can't be written, the harvester keeps its limiter in the run directory instead (`<run directory>/rate-limits`). The run's own agents still share one pace; only pacing across concurrent runs on the machine is lost, and the summary says so.

**When the harvester can't run.** The agent sends the requests itself, under the existing rules, only when:
- `uv` is missing;
- `uv` fails before the script starts (for example, it can't install the dependencies);
- the harvester exits with its setup-error status for anything but a usage error. Its message names which: the agent fixes a usage error and reruns.

The coverage ledger's reason for each such route says the agent sent them itself. Those requests, Semantic Scholar's included, get the one retry of any request the agent sends itself, not the harvester's longer schedule. A service whose key the run directory's state records as rejected gets no requests from the agent either.

**Running a query again.** A query that didn't run may go through the harvester again in a later snowball round, which is a new search rather than a retry. A query that ended `invalid input` or `client error` may be corrected and rerun at once, since the fault was in the query. Any other failed query waits for a later round, so a request gets no more retries within a round than the harvester gave it.

**Transport.** The harvester installs its own adapter, a subclass of the fork's rate-limited adapter, on every connector session through `http_limits.set_adapter_factory`. Every request a connector sends passes through it, including each redirect hop, and the adapter:
- paces each request through the fork's limiter, with a `max_wait` of 60 seconds, since a batch script, unlike an MCP server, can afford to wait;
- refuses, without sending:
  - a request to any host other than the three that the harvester registers limits for (`export.arxiv.org`, `api.openalex.org` and `api.semanticscholar.org`);
  - any request with TLS verification turned off;
- sets the skill's user agent (Rate limits in `references/sources.md`) on every request, replacing a connector's own, which can be a random browser string or a placeholder address;
- removes an `Authorization` header from any request to a service other than OpenAlex, so `requests` can't attach `~/.netrc` credentials there, and an `x-api-key` header from any request to a service other than Semantic Scholar;
- refuses a request that isn't plain `https` on the default port;
- gives each distinct request (its method and full URL) a fixed number of attempts within a query: two (the first and one retry) on arXiv and OpenAlex, and seven (the first and up to six retries) on Semantic Scholar. A further attempt is refused without being sent, whatever retries the connector tries itself;
- within a query, serves a request that already succeeded from memory instead of sending it again. So when the harvester calls a connector again to retry a query (a connector that doesn't retry by itself, or one that fetches several pages), only the failed request is resent;
- times each retry from the failed response:
  - it waits until `Retry-After` has passed, in seconds or as an HTTP date. A date in the past means no wait, and a value it can't parse counts as absent;
  - on arXiv and OpenAlex, after a rate-limit response with no `Retry-After`, it waits 15 seconds, and after any other failure, only for the next slot;
  - on Semantic Scholar, after any failure that allows a retry, it waits a backoff that grows with each retry: 1.5 seconds times 1.6 to the power of the retries already sent, plus a random jitter of 0 to 0.75 seconds, the sum capped at 15 seconds. The jitter comes from a random source that tests can fix. A `Retry-After` that ends later than the backoff wins;
  - on every service, the wait and the limiter's next slot overlap: the retry goes at the later of the two, not their sum;
  - time the connector already spent sleeping counts toward the wait;
  - when `Retry-After` asks for more than 60 seconds, there is no retry;
  - on Semantic Scholar, there is no retry when, at the moment it would be sent (after its wait and limiter slot), more than 60 seconds have passed since the request's first response or failure arrived;
- records each attempt in the query log: its time, URL, HTTP status (or the exception's class for a network error), the wait before it, and whether it was refused or served from memory;
- saves each response body under the run directory.

The harvester itself calls a connector again for a query when the query hasn't run, its failed request has attempts left, and the failure allows a retry. A rate-limit response, a 5xx, a network error or a 2xx whose body doesn't parse allows one; an authentication failure, a client error, a `not found` and an OpenAlex budget response (below) don't. The `recommend` and `lookup` requests, which the harvester builds itself (see Semantic Scholar endpoints), are resent by the harvester directly under the same rules: the same attempt count, timing, logging and classification.

Since the adapter times every resend, the harvester turns the connectors' own sleeps between retries into no-ops; one connector would otherwise sleep for whatever `Retry-After` a service sends, a whole day for a spent quota. Citations and references lookups get the longest time budget the fork's relations lookup allows (60 seconds), since that budget runs on the real clock and includes the adapter's waits. Connectors catch broad exceptions, so an error of the harvester's own inside the adapter (a full disk while saving a body, say) is kept aside and raised again once the connector returns, to end as `internal error` rather than pass as a network failure.

**What counts as what.**
- **Rate-limit response:** any of:
  - a 429 or a 503;
  - arXiv's HTTP 200 whose body begins "Rate exceeded";
  - a 403 that carries `Retry-After`, has a remaining-quota header (`X-RateLimit-Remaining` or `X-Rate-Limit-Remaining`, in any case) of 0, or whose body says "rate limit", "too many requests" or "quota".
- **OpenAlex budget response:** an OpenAlex 429 whose body says "budget" or "plan upgrade", ignoring case. Other statuses with those words are judged by the rules above. The daily budget it reports spent doesn't refill until the next day, so it is a rate-limit response that gets no retry.
- **Authentication failure:** a 401, or any other 403. It gets no retry.
- **Query ran:** every request the query needed got a usable response:
  - a redirect, which `requests` or the connector then follows;
  - a 2xx whose body parses (JSON from OpenAlex and Semantic Scholar, an Atom feed from arXiv), except arXiv's "Rate exceeded". A `recommend` or `lookup` body parses only when it holds its list of papers, so a body without one is retried like any other that doesn't parse;
  - an arXiv 406 that the arXiv connector's own check accepts as a feed of results;
  - or, for a `lookup`, a 404 whose JSON body's `error` is "Title match not found".
- **Outcome:** each query ends with exactly one. A connector's return value never decides it, because some connectors turn a failure into an empty list. When a query that made several requests didn't run, its outcome comes from the first request that failed, and a request whose attempts failed in different ways is judged by its last attempt.
  - `ok`: it ran and found results. `empty`: it ran and found nothing.
  - `not found`: the paper ID of a citations, references or recommendations query doesn't exist (a 404). A lookup whose title matches no paper ran and found nothing, so its outcome is `empty`; any other 404 on a lookup is a `client error`.
  - `rate limit`: its last attempt got a rate-limit response, or a rate-limit response allowed no retry (`Retry-After` asked for more than 60 seconds, a Semantic Scholar retry would have gone more than 60 seconds after the request's first response or failure arrived, or it was an OpenAlex budget response).
  - `authentication`: an authentication failure.
  - `client error`: any other 4xx, such as a 400 for a query the service can't parse. It gets no retry.
  - `network`: a connection error or timeout, a 5xx other than 503, a 2xx whose body doesn't parse, or a connector's own request error (such as an OpenAlex seed lookup that returns no work ID) although every response was usable.
  - `internal error`: any other exception, from the harvester or a connector. A crash is a bug to fix, not an outage. That query and the ones not yet handled get this outcome, and the harvester logs the error and exits with status 3, or with status 4 when it had sent nothing, so the agent's fallback never repeats a request.
  - `not sent: limiter wait`: the limiter would have waited longer than `max_wait`, or its store stayed locked that long. Nothing was sent, so the service isn't marked throttled. When the limiter blocks only a retry, the service's own failed response decides the outcome, as for any retry the adapter withholds.
  - `refused`: the adapter refused it. The query log gives the reason (host, TLS, a missing key, a rejected key or `daily budget`). A rejected key outranks a spent budget, since it lasts beyond the day and needs the developer to act.
  - `skipped: service throttled`: see Services that fail.
  - `invalid input`: an OpenAlex search with more than 5 boolean operators, a paper ID the citations and references lookups don't accept (only DOIs and OpenAlex work IDs), or a seed the recommendations don't accept (see Semantic Scholar endpoints). Nothing is sent.
- **Truncated snowballing:** a citations or references query that stopped at the connector's page or request budget records that, with the connector's stop reason, in the query log and its summary line.
- **Quota headers** don't lower the pace. The harvester paces to the stated limits and reacts only to rate-limit responses, so no spec covers the headers beyond the rate-limit rules.

**Limits.** The harvester registers its own limits over the fork's table, from the figures in `references/sources.md`'s Rate limits section:
- arXiv: 1 request every 3 seconds.
- OpenAlex: 10 a second, or 30 a second for a request that carries its key.
- Semantic Scholar: 1 request every 8 seconds, or 1 a second when its key is set. The fork's limit holds one window per service, so it can't express both. The harvester registers the anonymous limit, or the keyed one when the key has a value. The fork counts keyed and anonymous requests in separate buckets, so the two windows never mix.

The OpenAlex connector sends the key as an `Authorization: Bearer` header. OpenAlex accepts that in place of the `api_key` parameter that `references/sources.md` names for requests an agent sends itself, and it keeps the key out of URLs.

**Semantic Scholar endpoints.** The connector has no method for either Semantic Scholar action, so the harvester sends both through the connector's session, which carries the harvester's adapter, and parses each paper with the connector's own parser:
- `recommend` sends `GET /recommendations/v1/papers/forpaper/<seed>` with `from=all-cs`, since the endpoint's default pool holds only recent papers. A seed, trimmed of surrounding whitespace, is a DOI (bare, with a `doi:` prefix in any case, or an `http` or `https` `doi.org` or `dx.doi.org` URL without a query string or fragment, as the citations lookup also requires), sent as `DOI:<doi>`; a new-style arXiv ID (`NNNN.NNNN` or `NNNN.NNNNN`, bare or with an `arXiv:` prefix in any case, any version suffix such as `v2` or `V2` dropped), sent as `arXiv:<id>`; or a 40-character hexadecimal Semantic Scholar paper ID in either case, sent in lower case. Old-style arXiv IDs (such as `hep-th/9901001`) aren't accepted: the skill's searches look at recent papers, and one rule is simpler to check. The seed is percent-encoded in the path, except for `:` and `/`, which Semantic Scholar's IDs use;
- `lookup` sends `GET /graph/v1/paper/search/match` with the title, trimmed of surrounding whitespace, as its query. It returns the closest title match with a match score, or a 404. The closest match can be a different paper, so the harvest record carries the match score and the matched title, and the agent compares the title, ignoring case, punctuation, whitespace and accents, before using the result.

Both requests ask, in their `fields` parameter, for the fields the connector's parser reads, since Semantic Scholar otherwise returns little more than the title. The key goes in the `x-api-key` header, as the connector sends it. Both endpoints are on `api.semanticscholar.org`, so they share that host's one limit.

The limits live in a shared directory, `~/.cache/prior-art-search/rate-limits/` (under `$XDG_CACHE_HOME` when that is set). So they hold across every harvester process the developer's user account runs, in any repo, except in a sandboxed shell that can't write there (see Running it). One gap remains: the fork counts keyed and anonymous requests in separate buckets, so two runs on one machine, one with a key and one without, can together exceed the keyed limit. The run's agents still give each service to one agent at a time (Steps, step 5), because requests the agents send themselves don't pass through the harvester's limiter.

**Services that fail.**
- After a query ends `rate limit`, the harvester sends nothing more to that service in this invocation, and gives each remaining query for it the outcome `skipped: service throttled`. The agent doesn't invoke the harvester for that service again until the next snowball round, so a request's retries aren't extended across invocations, and the service's substitute route covers the gap meanwhile.
- On Semantic Scholar, a query that ends `network` because its last attempt got a 5xx stops the service the same way, since Semantic Scholar answers with 5xx as well as 429 when it is shedding load. Without this, a service failing every request would spend a minute of retries on each query of a batch. Likewise, after any Semantic Scholar query ends `network`, the agent doesn't invoke the harvester for Semantic Scholar again until the next round: a request that failed for a full minute of retries signals an outage, not passing flakiness, and each new seed would spend another minute on it.
- An OpenAlex budget response stops OpenAlex for the whole run, not just the invocation, since the budget is daily. The harvester records it in the run directory's state file and from then on refuses every OpenAlex request without sending it, in every invocation using that run directory, with the refusal reason `daily budget`. The agent's own OpenAlex DOI and open-access lookups go on, since OpenAlex doesn't charge single-record lookups against the budget.
- An authentication failure on a request that carried the service's key means the key was rejected. The harvester records that in the run directory's state file, so it holds for every agent of the run. From then on, in every invocation using that run directory, the harvester refuses every request to that service without sending it. The state file is read under a shared lock before each request and rewritten under an exclusive one, so a concurrent reader never sees it half-written, and a state file the harvester didn't write is an internal error rather than a record of no rejections.
- When a setting has a value, the harvester refuses any request to that service that doesn't carry it, so access can't silently fall back to anonymous.

**Credentials.**

*Finding and reading the settings file.*
- The settings file is `.config/prior-art-sources.toml` at the top of the git repository containing the working directory.
- Outside a git repository, or without `git`, the harvester runs as if there were no settings file.
- A settings file that git ignores but that is malformed, unreadable, or holds a setting the harvester uses whose value isn't a string stops the harvester with its setup-error status, naming the file and the problem but no value. Running on without it would silently switch a keyed service to anonymous access.
- It reads the file itself, with `tomllib`, under the same rules as the agent: only when git ignores the file, and never from any other source.
- A blank value counts as not set.

*Preparing the environment.* Before any connector creates a session or reads a setting, the harvester changes its own process environment:
- It removes every variable the fork reads for these services and for its limiter, both bare and with the `PAPER_SEARCH_MCP_` prefix: `OPENALEX_API_KEY`, `OPENALEX_EMAIL`, `SEMANTIC_SCHOLAR_API_KEY` and `RATE_LIMIT_DIR`.
- It sets `PAPER_SEARCH_MCP_RATE_LIMIT_DIR` to the shared directory.
- It sets `PAPER_SEARCH_MCP_ENV_FILE` to a path that doesn't exist, so the fork doesn't load its own settings file.

*Passing the values.*
- The OpenAlex key goes to the OpenAlex connector's constructor.
- The harvester puts the Semantic Scholar key in the `x-api-key` header of each Semantic Scholar request it builds, since it sends those requests itself rather than through a connector method.
- No value appears on the command line.

*Redaction.* Everything the harvester writes passes through one redaction step that replaces every non-blank value in the settings file with `[redacted:<setting>]`: what it prints, the query log, saved bodies, records, the connectors' log lines and exception messages. It matches each value as written, percent-encoded (either case, with `+` for spaces), JSON-escaped and as a Python repr, longest first. JSON records are redacted string by string before they are serialized, so a short value can't break a line's JSON. A value holding a control character is refused when the file is read, since a log would show it escaped. The harvester reads its settings before its command line, so a usage error that echoes a pasted key is redacted too. It writes no request headers anywhere.

**Output.** In the run directory:
- `queries.jsonl`, the query log: one line per query, with its ID, round, service, route, action, the query text or paper ID, the attempts, the outcome, a reason when the outcome has one (a refusal's reason, or `daily budget` for a `rate limit` from an OpenAlex budget response), and the result count;
- `records.jsonl`: one *harvest record* per result. A harvest record holds the connector's paper fields (title, authors, year, venue, DOI, arXiv ID, the service's own ID, abstract, citation count, URLs), plus the query ID and the result's rank, and for a lookup the match score. It isn't a paper record (Verification), which the agent writes only after reading;
- `ledger.jsonl`: one ledger record (Verification) per route per invocation, with the invocation ID;
- `raw/`: the saved response bodies, one file per attempt, named by query ID and attempt number;
- `harvest.log`: the connectors' log lines;
- `state.json`: the rejected keys, and whether OpenAlex's daily budget was reported spent.

On standard output, the harvester prints a summary the agent reads instead of the files:
- one line per query: its ID, service, query text, outcome and result count;
- under each query that ran, one line per result for its top results (10 by default): rank, year, citation count, the service's ID, and the title cut to 100 characters, then a line giving how many more are in `records.jsonl`. A result already shown earlier in the same invocation is shown only by its ID;
- the invocation's ledger lines and the paths of the files above.

**Exit status:** 0 when every query ran; 3 when any query didn't run; 4 for a usage or setup error, in which case nothing was sent. The harvester avoids 1 and 2, which `uv` itself uses when it fails before the script starts.

**Ledger state.** In each invocation, a route is *searched* when at least one of its queries ran, and otherwise *unavailable*. The diagnosis for an unavailable route comes from its last failed query, in the skill's wording:

| Outcome | Diagnosis |
|---|---|
| `rate limit` from an OpenAlex budget response, `skipped: service throttled` after one, and `refused` for `daily budget` | "rate limit (daily budget)" |
| `skipped: service throttled` after a Semantic Scholar query ended `network` | "network" |
| any other `rate limit` or `skipped: service throttled` | "rate limit", or "rate limit, no key set" when the service has an optional setting with no value |
| `not sent: limiter wait` | "rate limit (local pacing)" |
| `authentication` | "authentication: `<setting>` rejected" when the request carried a key; otherwise "authentication" |
| `refused` because the key was rejected | "authentication: `<setting>` rejected" |
| `network`, `internal error`, or `refused` for any other reason | "network" |

A route whose queries were all `invalid input`, `client error` or `not found` gets no ledger record, and those outcomes never make a route unavailable: the fault lies with the query or its paper ID, not the route.

Across invocations, the agent's ledger keeps a route *searched* once any invocation searched it. A later invocation's failed queries are listed with that route as failed, with their diagnosis, and don't change its state.

**Measuring it.** The search behind [the federated knowledge and work items note](../../prior-art/2026-11-06-federated-knowledge-and-work-items.md) recorded its queries but not each subagent's tokens, so the harvester is judged by a paired run instead: two subagents get the same need and the same fixed set of that search's literature queries and OpenAlex citation lookups, each sent to a service the harvester then covered for it, with the same task (name the results that address the need). One sends the requests by hand under the rules for requests an agent sends itself; the other uses the harvester. They run one after the other, so neither shares a service with the other, and they are compared on subagent tokens and on queries lost (given but neither run nor reported as failed). The result goes in `docs/review-log.md`.

## Verification

**Licenses.** The license is read from evidence the author controls, in this order:
1. the license file (`LICENSE`, `LICENSE.md`, `LICENSE.txt`, `COPYING` and similar);
2. the license field in the package manifest (`Cargo.toml`, `pyproject.toml`, `package.json`);
3. the README or file headers.

The note cites the file and line it used. A forge badge or forge API metadata is only a pointer. Further rules:
- The license is recorded at the commit actually read, and for the paths actually used. A monorepo package's own license file takes precedence over the root one.
- An "OR" license records every option.
- Vendored directories under another license are flagged.
- A "no license" finding cites the file listing it was based on, read at `full` depth. A candidate without a license can be borrowed from as an idea, but never adopted or built on.
- Source-available licenses are judged against the hard criteria set in step 2.
- The license file is read whole, at `full` depth (see Read depth), not just its first line, in a quick pass as in the full method. Registries, badges and the file's own heading can say "MIT" for a file that adds terms below the standard text: the Commons Clause, a restriction on use, or a rider about AI training or AI vendors. The agent searches the file for such additions ("Commons Clause", "rider", "restriction", "additional terms") and records any it finds as part of the license, which makes it source-available rather than the base license. Like any source-available license, it is judged against the hard criteria for how the host repo will use and distribute the result, and the report names the added terms. A license read only at `snippet` depth leaves the license criterion `unverified`, and a candidate whose license is `unverified` isn't classified **adopt** or **build on**: an unread rider is exactly what a summary misses, and a full read costs one request. Wording of the standard text (MIT's "without restriction") and SPDX-listed exceptions (a GPL linking exception) aren't added terms.

**Source.** When the agent verifies a candidate in source (step 9), it reads the code from these sources in order:
1. the host repo's reference-clone convention, if the host's instructions name one, read at the commit it holds;
2. the forge's contents API (for example `gh api`), for a few files, when authenticated;
3. a shallow, read-only clone into a new, empty directory under the agent's scratch or temp directory, outside the host repo. The clone:
   - uses `git clone --depth 1`, with no submodules and with `GIT_LFS_SKIP_SMUDGE=1`;
   - for a large repo, adds `--filter=blob:none --sparse`, then runs `git sparse-checkout set <dirs>`;
4. for a candidate with no reachable forge, the package registry's published source archive, downloaded and extracted without being built.

Every reading records the resolved commit SHA, or the archive's version, so each `path:line` it cites is pinned. Cleaning up scratch clones is optional.

**Read depth.** A reading is `full` only when the agent has the whole text of what it read, unshortened, from a clone, the contents API, a local file, or a raw file or verbatim endpoint (a `.md` docs page, `llms-full.txt`, docs.github.com's article API) fetched with a tool that returns it unchanged, such as `curl`. A fetch tool that summarizes or truncates the page (Claude Code's WebFetch does both) gives `snippet` depth whatever URL it fetched, and so do web search results. The rule applies to the agent's own readings and its subagents' alike, and to a paper's *read in full* state.

**Untrusted content.** Candidate repos, pages and catalog entries are data, not instructions. The agent never installs, builds or runs a candidate, or a script from one, during evaluation. It never follows instructions found in candidate content, and it never sends credentials or the host repo's private content to a candidate or its service.

**Lookalike copies.** Search results sorted by update time surface copies of real tools that aren't marked as forks: the same description and license copyright holder as another project, with a README that tells users to download and run an installer instead of building the code. Either sign alone is a cue for a serious candidate: a description or copyright holder matching another project's, when the candidate's own owner isn't that holder, or an installer-only README, whoever the owner is. The cue is to look for an original by name, not to reject, since legitimate desktop tools also ship installer-only READMEs. The original is, in order of preference, the repo whose owner matches the license's copyright holder, the repo that the tool's package registry entry or official site links to, or the earliest-created repo with that name and description. When an original is found, the agent rejects the copy, naming the original as the reason, and adds the original as a serious candidate in the current round if it fits the need. When none is found, the agent evaluates the hit on its merits but flags it in the report as a possible copy, and doesn't classify it **adopt** or **build on** without the developer's review (in a non-interactive run, the report asks for that review).

**Subagents.** When the agent fans out the work (one subagent per route group, or one per candidate to read its source), each subagent returns only structured records:
- **Evidence records:** `{candidate, url, criterion, claim, support, evidence, evidence_kind, read_depth, commit, as_of}`.
  - `support` is one of the five support values.
  - `evidence` is a URL or a `path:line`.
  - `evidence_kind` is `source`, `manifest`, `docs`, `metadata` or `listing`. A negative claim ("no clone step anywhere in `references/`") is a `listing`, whose evidence is the search command and its scope.
  - `read_depth` is `full` or `snippet`. A `snippet` record can support a lead or a docs-only claim, never a *verified in source* tag or the step 9 verification of a candidate. Read depth (above) decides which.
  - `commit` is the SHA or archive version read.
  - `as_of` is an ISO date.
- **Ledger records:** `{route, state, queries, reason, as_of}`.
- **Paper records:** `{paper, doi, url, claim, read_state, evidence_strength, review_status, as_of}`, with the value sets of Searching the literature. `read_state` is the paper's read state, which is distinct from an evidence record's `read_depth`.

The main agent builds the matrix and the ledger only from these records and its own readings.

## Report

The report starts with one verdict:
- **adopt** *X*;
- **build on** *X*;
- **blend**: *X* plus *Y*, or *X* plus a named custom piece;
- **build**, borrowing ideas from the listed candidates, or from none;
- **findings**: for a need about approaches with nothing being built, the approaches found, with their papers and tags, in a quick pass or the full method. The forge, registry, catalog and skill-catalog routes are excluded ("no software sought"), while general web search and the local routes still run, and steps 8 to 11 are skipped. Its report gives the verdict, the papers table, "Worth retrieving manually", the coverage ledger and what the developer already knew, with no shortlist, matrix or "Verified" list. It is **inconclusive** instead when the developer stopped the search, or a triggered literature route is unavailable and its substitute wasn't searched;
- **inconclusive**: the developer stopped the search, or nothing fits but the ledger can't support **build**, because a triggered route is still unavailable (other than a literature route whose named substitute was searched) or the round cap was reached while rounds were still adding serious candidates. The report names what's missing and, when the cap was reached, lists the open leads;
- **unaudited**: a quick pass forced by the developer that would otherwise have escalated.

Then come:
- a ranked shortlist with one line each on why it ranks where it does, and what would change the ranking;
- the matrix;
- "Verified" and "Could not verify" lists;
- the coverage ledger, with each selected route's state and queries or reason;
- when papers were candidates, a "Worth retrieving manually" list (see Searching the literature).

Every report, at either level, also says what the developer already knew about or had dismissed, or that step 0's question went unanswered; gives the common uses from step 1, or that the question went unanswered and the uses inferred instead; names any terms a candidate's license adds to its standard text; and flags any candidate that may be a lookalike copy with no original found.

**Links.** The report and the note name each software candidate and each paper as a Markdown link at its first mention in each section and in every table row, with the name as the link text, so a reader never has to search for what the agent already located. The target is the best link the agent found: for software, its repository, or its official page when it has no repository; for a paper, its open-access page when one exists, otherwise its DOI link, otherwise its publisher's or preprint server's page. The agent opened the target or took it from the page where it found the candidate, and never composes one from memory. A full URL isn't shown as link text. When no link was found, the report says "no link found" beside the name.

**Build** requires a "nothing fits" result that the ledger supports. Every triggered route is searched, excluded with a reason tied to the need, or excluded as blocking scripted clients with its named alternative searched, none is unavailable, and the last round added no serious candidate. An unavailable literature route whose named substitute was searched doesn't count against this. An unavailable route blocks only **build**: any other verdict stands, with the route listed under "Could not verify".

**Saving.** A full-method run saves a note. The agent writes the file but never stages or commits it. The path is `<dir>/YYYY-MM-DD-<topic>.md`, where `<topic>` is a short kebab-case name for the need (not for a candidate). `<dir>` is resolved against the repo root and is the first of these that applies:
1. the directory the host repo's instructions name for research or prior-art notes, created if missing;
2. an existing `docs/prior-art/`;
3. an existing `research/` or `docs/research/`;
4. a new `docs/prior-art/`.

A note on a topic that already has an earlier-dated note links it under "Supersedes". A second note on the same topic and day updates that day's note. When the agent can't write the file, or isn't in a repo, it prints the whole note in the conversation and says it wasn't saved.

The note follows `references/note-template.md`. Its sections are:
- the need and criteria;
- the verdict;
- the candidate table and the matrix;
- the limitations checked in source;
- the coverage ledger with its queries;
- the snowball rounds, each with the serious candidates it added, and whether the cap was reached;
- when papers were candidates, a papers table (read state, evidence strength, review status, class) and the "Worth retrieving manually" list;
- a refresh trigger (a date, a version or an event), when the note backs a recorded decision.

**Private content.** In every repo, search queries are built only from the stated need (step 5), because they go to outside services. What a note may cite depends on the host repo's visibility. The agent treats the host repo as private when the forge reports it private or the host repo's own instructions say it is, and as public otherwise, including when the forge can't be asked:
- **In a public repo,** the note contains only public sources, the developer's stated requirements, and material the developer approves for it. If it would contain material the developer marked private, then in an interactive run the agent asks the developer whether to include it before saving. In a non-interactive run, it omits the material and records in the note that something was omitted.
- **In a private repo,** the note cites internal sources where they support a finding, such as the host's own code, its decisions and other private repositories.

## Testing

**Structure tests** run with pytest in CI:
- the frontmatter keys are exactly `name`, `description` and `license`;
- `name` matches the directory, and `description` is non-empty and at most 1024 characters;
- `SKILL.md` is under 500 lines, and every file it references exists;
- `plugin.json` and `marketplace.json` agree on the plugin's name, and the marketplace entry's `source` is `./`;
- the reference files contain the pieces the specs require: the route table's columns, the record shapes, and the note template's sections;
- `sources.md` has literature routes whose trigger is a question about an approach, each with a substitute that is a different literature route, and an access-settings section that names the setting each route uses and tells a host repo to ignore the settings file;
- the skill's `references/settings.example.toml` has every setting that `sources.md` names (in backticks as `section.key`), each with the value `""` and a comment marking it `required` or `optional`, saying where to register or that no registration is needed, and where its terms are or that they weren't read, and git ignores the real `.config/prior-art-sources.toml` in this repo.

**Behavior evals** run by hand with `claude plugin eval`. They aren't in PR CI, because each run costs model calls. Each run is isolated, with no user-level or project instructions, so none can already require a prior-art search, and every case also runs in the no-plugin baseline arm, so a pass shows the skill made the difference. Cases are tagged `online` or `offline`: the offline cases work from local fixtures, which makes license edge cases, untrusted content and unavailable routes repeatable. Graders check the contract, not exact candidates, because web results drift. The cases:
- **Trigger cases:** the skill fires for "write a tool that does X" and stays quiet for a bug fix.
- **Contract cases:**
  - a stated effort level with its reason;
  - a ledger in which every selected route has a state;
  - licenses cited from a file;
  - limitations carrying their tags;
  - a verdict from the defined set;
  - **build** only when the ledger supports it.
- **Lock files on template updates.** The need: keep a consumer's committed `mise.lock` current when hosted Renovate's copier manager changes tool pins, since the hosted app can't run `mise lock` as a post-upgrade task. A good result:
  - is **build** or **blend**;
  - records that Renovate's post-upgrade tasks can't run `mise lock` on the hosted app;
  - finds aquaproj's update-checksum-workflow as a pattern to borrow.
- **Gap in a quick pass.** A quick pass whose best candidate leaves a core requirement unmet escalates to the full method, and one whose candidate needs only a small extension doesn't.
- **Snippet reads.** A subagent record with `snippet` depth doesn't make a candidate verified: the report doesn't tag a limitation *verified in source* on it.
- **Approach need.** A need phrased as "what approaches help achieve X" selects the literature routes, classifies papers as borrow ideas or reject, tags claims *paper-reported*, and lists a decisive abstract-only paper under "Worth retrieving manually" without a shadow-library route.
- **Access settings.** With no settings file, a route whose setting is required is recorded unavailable, and no value is invented. With a file, a planted fake value (a canary) never appears in the final output, the saved note, any subagent prompt or the literal text of any command. With a file that git doesn't ignore, the agent doesn't read it, asks whether to add the ignore line, and doesn't edit `.gitignore` without a yes.
- **Approach question.** A question about which approaches help, with nothing being built, gets a question about using the skill, and no search starts before the developer says yes.
- **Rate limits.** In the online literature case, no route gets requests faster than its stated limit, counting subagents' requests, and after a rate-limit response to a request the agent sent itself, it waits as long as the service names before its one retry. In the subagent case, no two subagents hold the same route and each prompt carries its routes' limits.
- **Nominal coverage.** The specs about an outage with a searched substitute, a throttled route with no key, and a decisive abstract-only paper depend on what a live service does during a run, so the online cases cover them only when the condition arises. The offline quick-pass cases don't assert a count of searched routes, because the network is down; the online cases cover that count.
- **Links.** The report and the note link every named candidate and paper by name, never as a bare URL, and say "no link found" where none was.
- **Shared config with per-repo overrides.** The need: share config files across repos, with committed key-level overrides per repo and gitignored local overlays. A good result is **blend** or **build on**. It records that no single tool covers both halves, and it finds at least one tool for each half, or a config language with an amends or override mechanism as a base.

**Harvester tests** run with pytest in CI and never reach the network. Connector responses come from a fake transport mounted under the harvester's adapter, and the limiter uses a temporary directory. They cover the transport rules, the outcome and ledger rules, redaction with a planted canary value, the output files and the summary, and the exit statuses. Subprocess tests run the script with `uv run --script` against its lock file, offline (`UV_OFFLINE=1`) after a setup step has filled uv's cache. They cover only paths that send no request: usage and setup errors, and the settings-file checks. The repo's dev dependencies pin the same fork commit as the script's header, and a test checks that the two pins match. Another checks that the harvester's limits match the figures in `references/sources.md`. CI fails when `harvest.py.lock` is stale. Renovate bumps the fork commit in both places through a custom regex manager using the `git-refs` datasource, and the developer refreshes the lock files on that pull request.

Each eval case carries `@spec` comments in its `case.yaml` for the EARS IDs it exercises. Specs that only an eval covers are marked *(eval)* in the specs file. `lidc` (0.3.0) reads `@spec` only in test code, so a pytest test carries the citations for every eval-only spec and checks that some eval case cites each one.

## Decisions & Alternatives

| Decision | Choice | Rationale | Alternatives considered |
|---|---|---|---|
| Build vs. adopt | Build, borrowing ideas from MIT-licensed skills | None of the twelve candidates found both verifies limitations in source and saves an auditable query log, and the closest take licenses from API metadata. See the prior-art note | Adopt search-before-build (product-oriented for non-experts, with an HTML viewer, and writes nothing to the repo); fork github-build-or-reuse (GitHub-first, with no source-reading or saving step) |
| What the skill adds over skill finders and scanners | Fitness comparison against the specific need | Retrieval tools find skills and scanners check their safety; neither compares candidates against a need | Rely on a skill finder plus a scanner for skill choices |
| Scope | Software, including agent skills, in one skill | The method is the same; skills differ only in their routes and three extra checks | Skills only (misses the common case of libraries and tools); general, with modes for purchases (different sources and criteria; deferred) |
| Effort | Quick pass vs. full method, chosen by door type, with escalation | Effort should match how costly a choice is to reverse. A full run on every small choice teaches agents to skip the skill | Always the full method; the developer picks every time |
| Search record | Coverage ledger: triggered routes, each searched, excluded with a reason, or unavailable | Makes "nothing fits" checkable, and keeps search effort proportional | A free-form list of queries (gaps are invisible); search every route every time (wasteful) |
| Snowball cap | Stop when a round adds no serious candidate, with a backstop of 10 rounds | Each round that finds a new serious candidate is evidence the search hasn't converged, so the cap is only a guard against a search that never settles. Saved notes record each round's new candidates, so the cap can be lowered if later rounds rarely add anything | A low cap such as 4 rounds (cuts off searches that are still finding candidates); no cap |
| How far to verify | The top 2-3, then on down the ranking until a candidate verifies as **adopt** or the rest fail a hard criterion that code can't change | Pre-verification rankings rest on READMEs and docs, which undersell some candidates and oversell others. Stopping at the top 3 would let a better candidate further down go unread, and a **build** verdict would rest on unread code | Always stop at the top 3 (cheaper, but misses candidates whose docs undersell them); verify every serious candidate (wasteful once one verifies as adopt) |
| Developer-forced quick pass | The developer's choice of level wins, and the verdict is **unaudited** | The developer often knows better than a rule how costly a choice is to reverse; the label keeps a shortened search from passing as a full one | Always escalate before concluding anything but **adopt** or **build on** |
| Private content | Queries never carry private content; notes in private repos may cite internal sources, notes in public repos may not. A repo is private when the forge reports it or the repo's own instructions say so | Queries reach outside services in every repo, while a note in a private repo is read only by people who can already see its sources. The repo's instructions are written by its owner and are readable without forge credentials, which cloud sessions often lack | Public sources only in every note (loses useful internal citations in private repos); the forge's report only (a private repo looks public wherever the forge can't be asked) |
| Quick-pass scope | A quick pass classifies and reads licenses only for the candidates it presents, and may exclude routes with the reason "quick pass" | A quick pass must stay quick; its gaps stay visible in the ledger, and it can't conclude **build**, so nothing rests on the unsearched routes. Escalation re-opens those routes | Every serious candidate's license and every triggered route even in a quick pass (makes a quick pass as slow as the full method) |
| Gaps in the search | An unavailable route or a reached round cap blocks only **build**, which becomes **inconclusive** | A gap weakens a "nothing fits" claim, not a candidate that verified; the developer can extend the search or accept the gap | Any gap makes every verdict inconclusive (discards verified finds); a reached cap still allows **build** (hides open leads) |
| Testing the chosen tool | Out of scope: the skill never runs a candidate, and trying out a chosen or already-adopted tool is separate follow-up work whose results a note may add under its own label | Running code is the riskiest step with untrusted repos, and a verdict should rest on reading; behavior tests belong to the developer's own evaluation of a pick | A "verified by running" evidence tag inside the skill, limited to tools the repo already uses |
| Criterion values | `native` / `partial` / `extensible` / `unsupported` / `unverified` | A criterion that is listed but never collected otherwise becomes a silent gap, and missing evidence gets read as absence | Yes/no cells; numeric scores |
| License evidence | License file, then manifest field, then README or headers | Forge metadata and badges are wrong often enough to mislead a classification; a manifest field is the author's own declaration | The forge API's SPDX field |
| Reading source | Host convention, then the API, then a scratch shallow clone, then the registry archive | Self-contained (tenet 7) and works in cloud sessions; uses a host's existing clones when present | Require a reference-clone skill as a dependency |
| Subagents | Optional, with fixed record shapes | Speeds up wide searches under Claude Code without making the skill depend on it (tenet 8); the shapes keep every claim sourced | Required fan-out; no subagents |
| Where notes go | Host-named directory, then an existing `docs/prior-art/`, `research/` or `docs/research/`, then a new `docs/prior-art/` | Respects each repo's layout, with a predictable default | Always `docs/prior-art/`; ask every time |
| Skill license | Apache-2.0, with the license text in the skill's own `LICENSE.txt` | Matches this repo and Anthropic's published skills; its explicit patent grant suits shared tooling; it can take in MIT-licensed code. APM installs only the skill's directory into each repo that uses it, and Apache-2.0 requires each copy to carry the license text, so the skill's directory holds it | MIT (the most common license for published skills, and shorter, but no patent grant); the license only in the repo root (copies would lose it) |
| Plugin `version` | Omitted from `plugin.json` | APM pins by tag, and a hand-kept version would drift from the tags | A version bumped each release |
| Plugin root | This repo's root, with the skills in a top-level `skills/` | The skill source sits outside `.claude/` and outside a wrapper directory, and APM installs the package by repository and tag. | `plugins/agentic-development/`, as LID lays out its plugin (an extra level for one plugin); a marketplace entry with `strict: false` and a hand-kept `skills` list (a list to keep in sync) |
| `@spec` placement | In tests, eval cases and the skill's scripts; `SKILL.md` and its references carry none | Annotations in skill text would be loaded into the agent's context on every run; a script is run, not read, so it is annotated like any other code | HTML-comment annotations in `SKILL.md` |

| Rate limits | Each service's stated limit, with its source, is listed in `sources.md`, with a separate limit for requests that carry the service's setting (a key or a contact address) where the service states one; the limit for the run's access applies, and covers the run's requests and its subagents' together, across every route on that service; subagents are assigned services, not routes; one request every 3 seconds where none is stated | Services count clients by IP or by person, not by agent, and arXiv's terms say the limit covers all machines under one person's control. Recommendations have no OpenAlex equivalent, and the exact-title lookup finds publisher-only landmark papers | Keep Semantic Scholar for searches with retries (spends minutes per query on a service that refuses searches most); also use it for citations of recent arXiv preprints (OpenAlex's coverage is close, and its reference lists are fuller); drop it (loses recommendations) |

OpenAIRE needs no key, has a high stated limit and covers the published literature | Semantic Scholar (refuses most searches at busy times); OpenAIRE plus [OpenCitations](https://opencitations.net) for citations (a further route, and on 2026-11-15 it returned no citations for an arXiv DOI) |

The idea is restated here, not its code | One retry, as on the other services (fails about half of keyed requests); [deeper-research](https://github.com/aidotse/deeper-research)'s 8 attempts 5 to 35 s apart (`deeper_research/net.py:108-140` at `d13d1fc`, MIT; about 140 s per request); CASRAI's doubling from 1 s to 30 s over 8 attempts (about 90 s); shortening a long `Retry-After` to 60 s and retrying, as novelty-check does (would retry a service that asked for a longer pause) |
| OpenAlex budget responses | A 429 whose body says "budget" or "plan upgrade" gets no retry, and the harvester sends OpenAlex nothing more for the rest of the run, recorded in the run's state file and diagnosed "rate limit (daily budget)"; the agent's own single-record lookups go on | OpenAlex's free budget is daily, so a retry within the run can't succeed; novelty-check treats the same bodies as final (`skills/novelty-check/scripts/novelty_check/net.py:199-202,218-220` at `a275af4`). With OpenAlex the default for search, a run spends more of that budget. Single-record lookups cost nothing against it ([CASRAI's OpenAlex guide](https://casrai.org/guides/openalex-api), read 2026-11-15) | Treat it as an ordinary rate limit (wastes a request, and the ledger hides why); stop only for the invocation (each later round spends a request finding the budget still spent) |
| Semantic Scholar 5xx | A Semantic Scholar query that ends `network` on a 5xx stops the service for the invocation, as a `rate limit` does | Semantic Scholar returns 5xx alongside 429 when shedding load (CASRAI's guide, section "Observed"), and with six retries per request a batch against a failing service would otherwise run for many minutes, past an agent's shell timeout | A time budget per invocation (a new clock to specify and test); guidance on batch size only (nothing enforces it) |
| Recommendations endpoint | `forpaper` with `from=all-cs`, one seed per request | The default pool holds only papers from about the last two months (deeper-research's `docs/external_services.md:137-138` at `d13d1fc`, docs only); novelty-check asks for `all-cs` (`skills/novelty-check/scripts/novelty_check/sources/s2.py:111-118` at `a275af4`) | The multi-seed `POST /recommendations/v1/papers` (fewer requests; open question) |
| Exact-title lookup endpoint | `/graph/v1/paper/search/match` | It is built for a title and returns one best match, so a lookup is one request with nothing to rank | A bulk search on the quoted title (put 13 of 16 landmark papers in the top 10 in the [catalogs note](../../prior-art/2026-11-04-agent-readable-catalogs-and-paper-sources.md)'s trial, so the agent still has to pick the match) |
| Judging a query's outcome | From the HTTP status the harvester's adapter recorded, never from the connector's return value | Some connectors return an empty list for a failed request, which would let a throttled query pass as "nothing found" and a route pass as searched | Trust the connector's result (hides failures); change the connectors (an upstream change for each, which the fork keeps minimal) |
| Retries in the harvester | On arXiv and OpenAlex, one retry per request within a query, after `Retry-After` (15 seconds without one after a rate-limit response); on Semantic Scholar, the longer schedule in its own row. No retry when `Retry-After` asks for more than 60 seconds; requests that already succeeded are served from memory when a query is retried; a throttled service gets no more requests that invocation | One retry keeps the skill's retry-once rule on services whose throttling passes, or whose searches have a substitute, without cutting off a query that fetches several pages. Serving earlier successes from memory lets the harvester retry a connector that never retries by itself without repeating requests that worked. Semantic Scholar's recommendations and title lookups have only a weaker substitute (OpenAlex's related works and title search), and only repeated retries get them through | Growing backoff on every service (slow, and probes services whose substitutes would serve); the connectors' own retries (they differ, and one falls back to anonymous access) |
| Shared limiter directory | Always on, under the user's cache directory; in the run directory only when a sandboxed shell can't write the cache directory | Services count requests by address, across every repo and agent on the machine, so per-run or per-repo buckets would let concurrent runs together exceed a limit. A sandbox that allows writes only inside the host repo would otherwise stop the harvester entirely; pacing within the run still holds, and the summary says what was lost | Off by default (each process paces alone); in the run directory always (each run paces alone); exit with a setup error in a sandbox (the harvester never runs where agents run unattended) |
| Run directory in a sandboxed shell | In a directory the host repo's git ignores, with uv's cache beside it; ask before ignoring one | A sandbox that allows writes only inside the host repo leaves no other writable place, and ignoring a directory changes the host repo, which the skill already asks about for the settings file | Inside `.git/` (never tracked, but sandboxes can block writes there); always send the requests yourself in a sandbox (gives up the harvester where it helps most) |
| Hosts the harvester may reach | Only the three services' hosts, as the fork's limit table lists them; everything else refused | One rule blocks shadow libraries, stray downloads and unpaced hosts, and needs no list of hosts to avoid | A block list of shadow-library hosts (misses new ones); no host check (a connector could reach anything) |
| Run directory | One per skill run, shared by its agents, with appends under `flock` and an ID for each invocation | A rejected key has to stop every agent of the run, and the coverage ledger is built from all of their queries. `flock` is released when a process dies, so a killed harvester never blocks the directory | One directory per agent (a key rejected in one agent's harvester wouldn't stop another's); a lock file (left behind by a killed process) |
| Quota headers | Not used to lower the pace | The stated limits are the contract; reacting to rate-limit responses covers the rest, and adaptive pacing that runs ahead of the stated limits is what got some candidates rejected | Lower the pace when the remaining quota is low (more code, for a case a 429 already covers) |
| Lock file updates | Renovate bumps the fork commit with a custom manager; CI fails until the developer refreshes the lock files | Renovate's `pep723` manager neither bumps a git-pinned dependency nor refreshes a script lock file, and a fork commit changes rarely | A workflow that refreshes the lock on Renovate's pull requests (needs a GitHub App, like the lock-refresh workflow; worth it only if bumps become frequent); no script lock (installs drift between hosts) |
| GitHub topics | Discovered through GitHub's topic search for the need's key terms and each serious candidate's name, and every fitting variant searched | A field's projects spread across near-identical topics. On 2026-11-15 the topic search listed `mdbook-plugin`, `mdbook-plugins`, `mdbook-preprocessor`, `mdbook-renderer`, `mdbook-theme` and more for "mdbook", while [the docs-site note](../../prior-art/2026-10-23-docs-site-search-and-graph-features.md) had searched only `mdbook-preprocessor` and missed repos under the others | Topics taken only from candidates' own tags (misses variants no candidate found so far carries); guessed topic names (the gap observed) |
| GitHub sort orders | Each round-1 repository search, `topic:` searches included, and each search of a topic variant first found in a later round, runs sorted by stars and again restricted to repos pushed in the 12 months before the run, sorted by update time; other snowball searches run sorted by stars | Star floors hide new and unstarred tools, and sorting by update time alone is mostly churn and spam, including lookalike copies ([#158](https://github.com/jmbowman/agentic_development/issues/158), [#156](https://github.com/jmbowman/agentic_development/issues/156)). Later rounds are seeded by candidates already found, which stars rank well | One order (each hides a class of tools); a star floor (drops the new tools a search most needs to find); both orders in every round (exceeds GitHub's search limit across rounds) |
| Query shape | Broad, short queries first, narrowed with the vocabulary the results use; one product or vendor per query | Agents default to long, specific queries that return little ([Anthropic's multi-agent research write-up](https://www.anthropic.com/engineering/multi-agent-research-system)), and an OR across several vendors returned only the first vendor's hits ([#158](https://github.com/jmbowman/agentic_development/issues/158)) | Long queries matching the need's wording (few results); OR across vendors (silently drops all but the first) |
| The developer's own uses | Asked for in step 1 and walked first in step 11 | A verdict passed two review waves on generic scenarios and failed both of the developer's common cases once named ([#196](https://github.com/jmbowman/agentic_development/issues/196)) | Generic scenarios only (the observed failure); a run test of the finalist (stronger, but a separate change: the skill never runs candidates during evaluation) |
| License riders | Read the whole license file and record any added terms as part of the license | Four repos labeled MIT by registries and badges carried AI-related riders, and one added the Commons Clause; only reading the whole file caught them ([#156](https://github.com/jmbowman/agentic_development/issues/156)) | Read the heading or the SPDX line (misses riders below the standard text) |
| Reads through summarizing tools | A fetch tool that summarizes or truncates, and web search results, give `snippet` depth only | WebFetch summarizes pages and truncates long ones, yet subagents recorded such reads as `full` ([#156](https://github.com/jmbowman/agentic_development/issues/156)); verbatim endpoints (raw files, `.md` docs pages, `llms-full.txt`, docs.github.com's article API) give the text itself | Trust the tool's output as full (records claims no one read) |
| Lookalike copies | Find the original by name, reject the copy and evaluate the original | A non-fork copy with a real tool's description and license copyright, and an installer-only README, surfaced through recent-activity search ([#156](https://github.com/jmbowman/agentic_development/issues/156)) | Treat each hit on its own (risks recommending a malware-style copy) |
| How source routes were chosen | Each route judged on 18 topics (earlier notes' topics, broad software topics and upcoming research areas), on what it adds beyond the baseline and on reliability; defaults, conditional routes and rejections are recorded in the [catalogs note](../../prior-art/2026-11-04-agent-readable-catalogs-and-paper-sources.md). Later searches' observations revise the table. A route whose service challenges automated clients, or whose `robots.txt` disallows the paths it needs, is marked "blocks scripted clients" and excluded, with an alternative named that reaches the same projects. A route whose endpoint the service has disabled names its replacement (package dependents through ecosyste.ms, since libraries.io has disabled them) | A route judged on one topic is judged by that topic's vocabulary, and a route that is often down adds a failed lookup to every search. Excluding rather than marking unavailable keeps a block that no agent can clear from blocking **build**, while the named alternative keeps the coverage. On 2026-11-15: PyPI's `robots.txt` disallows `/search*` and its search page answers with a "Client Challenge", while [its API docs](https://docs.pypi.org/api/) welcome programmatic use of the JSON API with an identifying user agent, and its maintainers say the challenge protects search from automated access ([Python Discourse](https://discuss.python.org/t/fastly-interfering-with-pypi-search/73597)); Codeberg's `robots.txt` disallows `/api/` and query-string search pages for every user agent, and its search API answered 429; lib.rs answers every path, `robots.txt` included, with a Cloudflare challenge and states no policy, and [its source](https://gitlab.com/lib.rs/main) (at `b386b4a`) throttles and 404s user agents that look scripted (`server/src/main.rs:632-679`) and has no repo license; its data derives from crates.io's public database dump (`data/page/data-processing.md:5`), which the crates.io row reaches, and the data bundle its README names isn't served; each as reported in [#158](https://github.com/jmbowman/agentic_development/issues/158) | Judge by catalog size or popularity (says nothing about candidates added); keep every route (a failed lookup per search) |

## Open Questions & Future Decisions

- **More scripts for routine search work** ([#157](https://github.com/jmbowman/agentic_development/issues/157)). The harvester (see Harvester) is the first. Each of the others waits on its own prior-art search, except the harvester's extensions, which [the harvest pipeline note](../../prior-art/2026-11-07-search-harvest-pipeline.md) already covers:
  - the harvester's other literature routes, and the skill's own clients for GitHub and the package registries, which that note's verdict includes;
  - a normalizer and merger. It maps every key (`web:`, registry and forge keys) to one canonical `owner/repo` or DOI, keeps the others as aliases, and takes the strongest tag across them. It also checks, before the note is saved, that every candidate tagged as able to change the verdict or the shortlist appears in the note or has a recorded reason for dropping it;
  - repo enrichment: licenses at a commit, last push and release, fork flags, registry presence, cheap pre-filters on hard criteria;
  - scholarly document processing: arXiv full text (HTML, then the PDF) with math kept, reference extraction, artifact links, and a read state for open copies that can't be fetched by machine (a TLS failure on an author's host, say), so the paper goes to "Worth retrieving manually" instead of being dropped;
  - a record validator and renderer for the ledger, the matrix and the papers table.

  The scripts' design is a section of this LLD, with spec IDs under `PRIOR-SCR-`. Promoting this LLD to a sub-HLD over child leaves, which renames every `PRIOR-` spec ID, is weighed when the next script is designed.
- **The remaining requests to the harvester's services.** The agent still sends some requests to arXiv and OpenAlex itself: OpenAlex DOI and open-access lookups, arXiv ID lookups and listing pages. They count toward the same limits, but don't pass through the harvester's limiter, so the two pace separately. The plan is to move them into the harvester, as Semantic Scholar's are, after which the agents send nothing to these services themselves and the rule that gives each service to one agent at a time can relax for them. Until then, an agent that sends one of these requests first waits out the service's interval after its last harvester invocation for that service.
- **Multi-seed recommendations.** Semantic Scholar's `POST /recommendations/v1/papers` takes several seed papers in one request, which [deeper-research](https://github.com/aidotse/deeper-research) uses (`deeper_research/fringe.py:211-214` at `d13d1fc`). Whether it accepts the `from=all-cs` pool, and whether its results serve snowballing as well as one seed at a time, needs a probe before `recommend` uses it.
- **Removing the fallback to the agent's own requests.** Once the harvester is integrated and verified on real searches, the rule that lets the agent send the harvester's requests itself (see Harvester, "When the harvester can't run") goes. The skill then needs `uv`, and has one way to send each of these requests instead of two.
- **Sharing services among subagents.** The harvester's limiter holds across processes, so subagents could share a service through it, instead of the rule that gives each service to one agent at a time. That rule stays while agents also send some requests to the same services themselves, outside the limiter.

### Deferred

- Choices that aren't software (purchases, providers), as a separate mode or skill.
- Model-backed evals in CI.
- Adding the settings file's ignore line to the repos that the copier template renders.
- Moving the plugin out of the repo root into a subdirectory. `claude plugin eval` counts every entry under the plugin directory toward a 20,000-entry cap, gitignored ones included, so this repo's own working files (scratch, clones read during searches, later reference clones) can block its evals ([tool feedback](../../tool-feedback/claude-plugin-eval.md)). [This repo's setup](../repo-setup/repo-setup-design.md) runs evals from a copy instead. A move has to be weighed against the reasons in the Plugin root decision, and APM's support for installing a package from a repository subdirectory checked in its source. It would also be a major version for consumers, whose pins and skill links change.
- A locally cached snapshot of the dblp bibliography (Creative Commons Zero, about 1 GB compressed, published monthly), refreshed monthly, to search computer-science venue papers that the live literature APIs reach unreliably. It holds titles, authors, venues, years and DOIs but no abstracts, and it needs a build step and a cache location, so it waits until paper searches show a gap that the live routes can't fill.
